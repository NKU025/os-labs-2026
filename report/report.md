## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

Lab1 让内核能够启动，Lab2 开始解决“内核怎样使用剩余内存”的问题。首先从设备树取得 RAM 范围，为物理页建立描述符；随后把可用页交给页分配器；最后在页分配的基础上提供字节级对象分配。

```text
设备树 → page_init → Page 数组与空闲区
                        ↓
          First-Fit / Best-Fit / Buddy
                        ↓ alloc_pages、free_pages
              简化 SLUB：kmalloc、kfree
```

这里有两条不同的线：页表负责把虚拟地址转换为物理地址，分配器负责决定哪些物理页可以交给调用者。`page_init()` 使用启动汇编已经建立的映射，并不重新创建页表。

### 3.2 功能的逐步实现

1. `init_pmm_manager()` 选择并初始化分配器。
2. `page_init()` 检测内存、安排描述符数组、排除保留区，再调用 `init_memmap()` 注册空闲页。
3. `check_alloc_page()` 执行当前管理器的自检。
4. `slub_init()` 建立对象缓存，`slub_self_test()` 验证两层分配。
5. 独立运行评分测试，并用宿主 GDB 单步观察 QEMU 的地址翻译过程。

默认管理器为 Best-Fit。`make PMM=buddy` 和 `make PMM=first_fit` 分别选择另外两种实现。Makefile 记录当前配置，切换管理器或测试编译选项时自动重新编译，避免仍运行旧镜像。

### 3.3 核心函数与模块

以下路径以 `code/` 为起点。

| 文件或模块 | 作用 |

| `kern/mm/pmm.c` | 选择管理器、实现物理内存初始化、调用自检 |

#### 实现与验证过程

先设置 `va_pa_offset = PHYSICAL_MEMORY_OFFSET`，计算设备树末地址与框架上界的较小值，向下对齐为 `maxpa`。`npage = PPN(maxpa)` 是物理页号上界，而不是 RAM 页数；描述符数量为 `npage - nbase`。

数组从内核末尾符号 `end` 之后开始，起点向上对齐。先将全部描述符标记为保留，再从数组末尾之后的第一个完整页开始，调用：

```c
init_memmap(pa2page(free_begin), free_count);
```

`pa2page()` 得到的是描述符地址，不是把物理页内容复制到数组。First-Fit 或 Best-Fit 的 `init_memmap()` 会清除可用页的保留标志并建立空闲链表。

本次默认 Best-Fit、128 MiB 镜像中，描述符数组起点为 `0x80248000`，`sizeof(struct Page) = 40`，共有 32768 个描述符，占 `0x140000` 字节。因此空闲区从 `0x80388000` 开始，到 `0x88000000` 结束，共 31864 页。这里的地址随内核布局变化，不是源码里硬编码的空闲起点。

除真实 QEMU 运行外，还用宿主测试替换设备树输入、地址映射和分配器注册接口，对实际函数体做了 11 项边界测试。覆盖了正常容量、上界截断、非对齐末尾、零大小、无效基址、范围溢出、内核越界、描述符空间不足和零空闲页，均通过。该测试用于检查初始化逻辑，不替代 RISC-V 上的集成验证。

#### 模块功能描述

First-Fit 按地址排列空闲块，分配时取第一个足够大的块。每个空闲块只有首页保存 `property`，表示这个块包含多少页。

| 函数 | 主要过程 |
| --- | --- |
| `default_init()` | 初始化空闲链表和空闲页计数 |
| `default_init_memmap()` | 清除空闲页的保留标志，在块首页记录长度并按地址插入 |
| `default_alloc_pages(n)` | 顺序查找首个足够大的块；取出前 n 页，把剩余部分留在空闲链表中 |
| `default_free_pages(base, n)` | 按地址插入回收块，检查前后是否物理相邻，能合并就合并 |

合并不是只比较“大小相同”，而是检查前一块的末尾是否等于后一块的起点。地址有序使相邻块判断比较直接。

**改进空间：** 当前查找和插入都可能遍历链表。可增加按大小分类的索引，或者用平衡树维护空闲块；Next-Fit 也能减少反复从表头开始搜索的开销。但这些方法会增加维护成本，而且 Next-Fit 不保证碎片更少。改进应结合分配规模和访问模式评价，不能只看单次查找速度。

课程原实现及其测试保持不变，64 MiB、128 MiB 下的管理器自检均通过。

### 4.3 实现 Best-Fit 连续物理内存分配

```text
正常状态下维持：

一、初始化和登记
1. init 清空链表与计数；init_memmap 检查 n>0 及页状态，初始化描述符，将整段登记为一个空闲块。
2. 块首页记录 property，设置空闲块标志；插入时维护地址顺序，按需要与相邻区间合并，避免重复登记同一范围。

二、分配
3. 从链表头开始遍历，记录最小满足块。只有发现更小候选时才替换，保持同长度低地址优先；遇到长度恰好等于 n 的块可提前结束。
4. 总页数不足或遍历未找到合适连续块时返回 NULL。空链表需要独立处理，不把 nr_free 非零当作一定存在节点。
5. 整块使用时摘除节点；需要拆分时，将原块前 n 页交给调用者，把 base+n 作为余块首页，记录剩余长度并插回正确位置。
6. 清理已分配块的空闲标志及相关状态，更新 nr_free。说明拆分后为什么无需打乱链表的地址顺序。

三、释放与合并
7. 恢复合法释放区间的页状态，按地址定位插入位置。
8. 先检查与前块是否物理连续，再检查合并后与后块是否连续；移动或摘除节点时避免继续使用失效的块首页。
9. 合并只改变块组织，不额外增加空闲页数。nr_free 对本次释放只增加一次 n。

四、约束和验收
10. basic_check()、best_fit_check()、课程注入脚本及评分脚本原样保留，不删除断言或调整预期输出。
11. 验证小块优先、同大小低地址优先、完全匹配、分裂余块、无合适块、前向合并、后向合并和双向合并；补充测试放在独立位置。
12. 在 64 MiB、128 MiB 配置下运行并保存实际输出；执行课程检查与评分。评分只代表其覆盖的检查，不替代扩展模块验证。
13. 解释线性 Best-Fit 的复杂度及产生小碎片的可能性，再讨论额外大小索引的收益与代价。
```

#### 实现与验证过程

空闲链表仍按地址排序，便于合并；分配时遍历链表比较 `property`，找到恰好匹配的块后提前结束。选中较大块时，将前 n 页交给调用者，余块保留在原位置。回收由 `insert_and_merge()` 统一处理，先与前一块合并，再检查后一块。

框架测试会临时保存并清空 `free_list`、`nr_free`，因此实现保留了这两个状态名称和对应约定。课程提供的 `basic_check()`、`best_fit_check()` 未作修改。

初始框架因缺少这两个状态和管理函数而编译失败；补齐实现后，默认管理器从 First-Fit 切换为 Best-Fit。`make test` 输出 `grading: 6 / 6 points`，`make grade` 中 Page Init、Best-Fit 两项均为 OK，总分 20/20。

**改进空间：** 当前查找复杂度为 O(k)，k 为空闲块数量。可以增加按块大小组织的树或分级链表，加快最佳块查找，同时保留地址索引用于合并。Best-Fit 也可能留下大量小碎片，不意味着它在所有负载下都优于 First-Fit。

### 4.4 Buddy System 伙伴分配器

**负责人：** 2413446-黄泓懿

#### 模块功能描述与 Spec

使用 0～15 阶空闲链表，第 k 阶管理 `2^k` 页块。初始空闲区可能既不按大块对齐，也不是二次幂长度，因此先拆成一组对齐的二次幂块。

申请 n 页时向上取整到二次幂，从足够大的阶开始找块，并逐级二分。释放要求传入原分配块首页和原申请页数；本实现不支持把一个已分配伙伴块任意拆开释放。申请 0 页或超出上界时返回 NULL。

```text
实现放在 kern/mm/buddy_pmm.c/.h，使用现有 Page 数组和物理页转换接口。请把按阶管理、块状态、拆分和伙伴合并写清楚，避免把“地址相邻”当成“互为伙伴”。

6. 设置已分配块首状态，按取整后的页数减少 nr_free；失败时不留下拆分到一半的状态。

7. 核对首页、阶与块范围。伙伴索引使用 index XOR (1UL<<order)，不是简单的前一个块或后一个块。
8. 只有伙伴在管理范围内、为相同阶的空闲块首时才合并。将伙伴摘链，以较低索引为新首页，阶加一继续检查。

13. 解释 3 页按 4 页分配、5 页按 8 页分配的内部碎片，并说明按阶查找、拆分和合并的成本。不要将教学实现称为完整 Linux Buddy。
14. 实现与测试分开组织，不用打印 PASS 替代断言。测试要求另行给出。
```

```c
peer = index ^ (1UL << order);
```

| 申请 1、2、3、4、5、8、17 页 | 验证非二次幂请求的取整及分裂 |
| 写入并逐字节核对不同数据 | 检测分配块重叠或越界覆盖 |
| 逐页申请到耗尽 | 检查容量计数和失败处理 |

该实现适合学习二次幂分裂与合并。它会产生内部碎片，例如申请 3 页实际占用 4 页；没有实现多内存区、并发锁等生产系统功能。

### 4.5 简化 SLUB 对象分配器

**负责人：** 2413446-黄泓懿

#### 模块功能描述与 Spec

对外提供 `kmalloc(size)` 和 `kfree(ptr)`，下层使用当前页分配器。小对象按 16、32、64、128、256、512、1024、2048 字节分类；大于 2048 字节的请求直接申请连续页。返回地址按 16 字节对齐，`kmalloc(0)` 返回 NULL，`kfree(NULL)` 不执行操作。

#### 模块实现提示词

```text
[PROMPT]
在现有页分配器上实现简化 SLUB，新增 kern/mm/slub.c/.h，提供 slub_init()、kmalloc(size_t size) 和 kfree(void *ptr)。目标是把页级分配与对象级分配连接起来，不引入 Linux 完整 SLUB 的多核和 NUMA 机制。

请先明确 slab 页首布局、槽位位置和对象生命周期，再实现代码。对象层不要直接调用某个特定页分配器的内部函数，应通过公共接口工作。

[RELY]
1. 下层为 alloc_pages/free_pages/nr_free_pages，可切换 First-Fit、Best-Fit 或 Buddy。
2. 通过现有虚实地址转换规则访问分配到的页；对象指针是内核虚拟地址，不是 Page 描述符。
3. Buddy 会向上取整页数。大对象需要保存原请求页数，释放时按原约定交回下层。
4. 当前为单核教学环境，slub_init 在物理页管理器初始化后调用一次，不在仍有存活对象时重置所有缓存。

[GUARANTEE]
- 小对象按 16、32、64、128、256、512、1024、2048 字节分入八个尺寸类，选择最小可容纳的类。
- 返回地址至少 16 字节对齐，页首管理信息与对象槽位互不重叠。
- 同时存活的对象互不覆盖；释放对象后槽位可复用，空 slab 将整页归还下层。
- 超过 2048 字节的对象用连续页保存管理头和有效数据。
- kmalloc(0) 返回 NULL，kfree(NULL) 直接返回；溢出或内存不足时申请失败，不破坏已有对象。
- kfree 返回类型为 void；对识别出的错误状态按项目断言处理，不另行承诺返回错误码。

[SPECIFICATION]
一、slab 与缓存组织
1. 页首保存标识、所属 cache、链表节点、空槽头指针、使用数和容量等管理信息，管理头大小向上对齐到 16 字节。
2. 容量按 (PGSIZE-HEADER_SIZE)/object_size 计算；最小尺寸类需要足够的分配位图位数，不能让槽位伸入下一页。
3. 用空闲槽自身前几个字节保存下一空槽指针，仅在槽位未分配时使用这些字节。
4. 维护每个尺寸类的 slab 集合。申请时找到有空槽的页；没有时向下层申请并初始化新 slab。

二、小对象申请与释放
5. 从 freelist 弹出槽位，更新位图与 used；释放时验证 slab 标识、槽位边界、对齐以及当前分配状态，再加入 freelist。
6. used 归零时先将 slab 从缓存链表摘除，再归还物理页，之后不再读取已归还页中的管理信息。
7. 说明位图有助于识别仍有效 slab 内的重复释放，但不代表能可靠检测任意伪造指针、已回收页或旧指针复用。

三、大对象
8. 计算管理头加请求长度前检查上界，按页向上取整，避免 size_t 加法或对齐溢出。
9. 在首地址保存大对象标识和原申请页数，返回管理头之后的对齐地址。kfree 必须找回原块首页，再用保存的页数释放。
10. 下层分配失败返回 NULL；不能先改变缓存状态，再留下未完成对象。

四、集成与验收
11. 在 pmm_init 的页分配器检查之后初始化对象层，再运行独立 SLUB 测试；不改写原课程评分函数。
12. 验证尺寸类边界、跨页增长、槽位复用、整页回收、大对象与内存不足，分别在三种下层管理器运行。
13. 解释尺寸类带来的内部碎片、缓存管理成本与大对象的连续页要求。明确没有实现 per-CPU 缓存、并发锁、NUMA 和构造析构回调。
```

```text
2. 同时申请 1、16、17、31、32、33、64、65、127、128、129、256、257、512、513、1024、1025、2048、2049、4096、9000 字节。
3. 对每个返回值检查非空和 16 字节对齐，分别写入不同数据模式，所有对象申请完后逐字节核对其有效长度。
4. 先释放偶数下标对象，再释放奇数下标对象，结束后检查空闲页数恢复，覆盖不同顺序的对象回收。

二、槽位复用和跨页增长
5. 申请两个 32 字节对象，保留其中一个使 slab 继续存在；释放另一个后立即申请同类对象，检查空槽复用。不要在整个 slab 已经归还后仍要求新地址一定相同。
6. 同时申请 300 个 32 字节对象，确认实际跨多个 slab 页。每个对象写入与下标有关的数据，完成全部申请后统一核对。
7. 分批释放全部对象，检查多个 slab 页均被回收，计数回到初始值。

三、内存不足
8. 先保留一个 64 字节对象并写入数据，再持续从下层分配单页直到耗尽，保存所有页面供恢复。
9. 检查需要新页的 2048 字节申请和 9000 字节大对象申请失败；再申请 64 字节对象，验证已有 slab 的空槽仍可使用。
10. 重新核对原对象数据，释放缓存对象并归还暂存页，确保失败请求未泄漏资源。

四、执行与结论
11. 在 First-Fit、Best-Fit、Buddy 下分别运行，并覆盖 64 MiB、128 MiB 两种容量，记录配置与实际输出。
12. 每组 PASS 必须在相应断言之后输出。必要时加定位信息，但不修改原评分预期、不吞掉异常。
13. 不直接向当前运行中的测试插入可能触发断言并终止内核的非法释放；如另测此类错误路径，应隔离运行并明确预期。正常通过不等于已验证任意非法指针。
14. 说明每组发现的错误类型和覆盖边界，避免把“总页数恢复”单独当作没有对象重叠或数据破坏的证据。
```

#### 实现与验证过程

每个 slab 使用一个物理页，页首存放管理信息，其余区域切分为固定大小的槽位。空闲槽位内部保存下一槽位指针，形成 freelist；位图记录槽位是否分配，用于检查非法槽位或重复释放。分配优先复用已有 slab，所有槽位用完后才申请新页。

释放时从对象地址向下对齐找到 slab 页首，核对对象边界和位图，再放回 freelist。一个 slab 的对象全部释放后，整页归还下层。大对象的页首记录原申请页数，释放时一次交还；因此下层为 Buddy 时也能按相同申请规模恢复伙伴块。

| 测试 | 验证目的 |
| --- | --- |
| 21 种大小，包括 16/17、2048/2049、4096、9000 字节 | 检查尺寸类边界和大对象路径 |
| 同时持有不同对象，写入后逐字节核对 | 检查容量、地址对齐和数据隔离 |
| 单 slab 槽位释放后再次申请 | 验证槽位复用 |
| 300 个 32 字节对象 | 验证跨多个 slab 的增长和回收 |
| 下层页耗尽后继续申请 | 新 slab 和大对象申请失败，但旧 slab 的空槽仍可使用 |
| 全部释放后比较空闲页数 | 检查整页回收和内存泄漏 |

上述测试在 First-Fit、Best-Fit、Buddy 下分别运行，每种管理器都测试 64 MiB 和 128 MiB。六次运行均输出 `[SLUB] ALL TESTS PASSED`，最终空闲页数恢复到各自测试前的值。

这是体现“页分配＋对象分配”的教学实现，没有实现 Linux SLUB 的 per-CPU 缓存、NUMA 或并发同步；缓存查找仍采用链表。

#### 关键调用路径与实测

选取 `dtb_init()` 中读取设备树 magic 的指令。本次反汇编为：

```asm
0xffffffffc020028a: lw a5,0(a4)
```

访问地址为 `0xffffffffc2200000`。在 `load_helper()` 入口设置 `addr == 0xffffffffc2200000 && !code_read` 条件，实测进入以下路径：

```text
TCG 生成的宿主代码
  → helper_le_ldul_mmu → full_le_ldul_mmu → load_helper
  → tlb_hit 未命中 → victim_tlb_hit 未命中
  → tlb_fill → riscv_cpu_tlb_fill → get_physical_address
  → tlb_set_page → 返回 load_helper 完成访存
```

`load_helper()` 位于 QEMU 的 `accel/tcg/cputlb.c`。这次 `mmu_idx = 1`，TLB 槽位原来的读标签为 `0xffffffffc0200000`，与目标页不一致，于是进入慢路径。

`get_physical_address()` 位于 `target/riscv/cpu_helper.c`。单步记录如下：

| 量 | 实测值 | 含义 |
| --- | --- | --- |
| `satp` | `0x8000000000080206` | 模式为 Sv39，根页表物理页号为 `0x80206` |
| `base` | `0x80206000` | 根页表物理地址 |
| `levels` / `i` | 3 / 0 | 支持三级，此时处于第一次迭代 |
| `ptshift` / `idx` | 18 / 511 | 当前使用最高级索引，选择第 511 项 |
| `pte_addr` | `0x80206ff8` | `base + 511 × 8` |
| `pte` / `ppn` | `0x200000cf` / `0x80000` | 页表项和页框号 |
| 返回物理地址 | `0x82200000` | 与设备树所在物理地址一致 |

这里没有走满三次循环。启动页表的最高级项已经是 **1 GiB 大页叶子项**，其 V/R/W/X/A/D 位为 1，因此直接完成权限检查和地址拼接。源码中“R/W/X 均为零”的分支才表示继续进入下一级页表。本次还依次经过用户/监督态权限、PPN 对齐和访问权限等检查，均未触发错误。

地址组合为：

```text
PA = (PPN | (VPN & ((1 << 18) - 1))) << 12
   = (0x80000 | 0x2200) << 12
   = 0x82200000
```

本次访问的页内偏移为 0。一般情况还要保留页内偏移，不能把上述页基址公式误当成任意字节地址的完整公式。

随后 `tlb_set_page()` 收到虚拟页 `0xffffffffc2200000`、物理页 `0x82200000`、权限 7、大小 4096。返回后，读标签已更新为目标页，`addr + addend` 得到宿主机中承载该数据的地址。读取出的原始 32 位值为 `0xedfe0dd0`，按设备树大端格式转换后为 magic `0xd00dfeed`。

#### 软件 TLB 与硬件 TLB 的区别

真实 CPU 的 TLB 缓存地址翻译和权限结果；QEMU 的软件 TLB 还要帮助把客体地址定位到宿主机内存，因而包含 `addend` 以及 RAM/MMIO 路径信息。TCG 的快速命中检查由 `tcg/i386/tcg-target.inc.c` 中的 `tcg_out_tlb_load()` 生成，不是每次命中都调用 C 的 `load_helper()`。

作为对照，在复位取指 `0x1000` 处也命中了 `get_physical_address()`：此时 `satp = 0`、`mmu_idx = 3`，直接返回物理地址 `0x1000`，未遍历页表。说明 QEMU 即使在未分页的访问中也可能使用自己的软件 TLB 路径；它不仅是客体页表翻译的缓存。这一对照观察的是取指，前面的 Sv39 观察是数据加载。

#### 调试中遇到的问题

最初把条件断点放在复位代码读取 `0x1018` 和内核读取 `boot_hartid` 的位置，未命中预期的页表遍历。结合代码检查，相关页已有更早访问，不能假设每条访存都会进入翻译函数。改为首次读取设备树 magic 的地址后，成功观察到未命中、查表和填充全过程。

另一个问题是 GDB 的 `until` 使用了没有可执行指令的源代码行，调试器直接返回调用者，随后查看局部变量时提示变量不在当前上下文。改为在 TLB 填充返回后逐行 `next`，即可看到更新后的 `entry->addr_read`。这些现象也说明调试时应核对当前位置，而不是机械照抄行号。

## 六、实验总结与收获

### 对操作系统的理解

本次实验把内存管理分成了三个层次：页表解决“地址指向哪里”，页分配器解决“哪些连续物理页可以使用”，SLUB 解决“怎样让小对象共享页面”。三者相关，但各自维护的状态和需要验证的性质不同。

| 实验知识点 | 对应的 OS 原理 | 联系与区别 |
| --- | --- | --- |
| `Page` 数组和保留区 | 物理内存管理 | 管理数据本身也占内存，必须从可用区扣除 |
| First-Fit、Best-Fit | 动态分区分配与外部碎片 | 本实验以页为单位分配连续块，算法思想与动态分区相通 |
| Buddy | 二次幂分割、合并与内部碎片 | 合并规则明确，但向上取整会多占页面 |
| 简化 SLUB | 对象缓存与分层分配 | 小对象复用同一页，回收整页仍依赖页分配器 |
| Sv39 与软件 TLB | 地址翻译与缓存 | 本次实际走的是最高级大页叶子，不是每次都读三级页表 |

页面置换、按需调页、进程调度、文件系统和多核同步仍是重要内容，但不属于本次分配器的实现范围。当前测试也不证明所有输入、并发情形或不同硬件平台均正确。

### AI 协作开发的经验

本次代码实现、测试执行和材料整理由 AI 辅助完成，结论以源码、断言和原始日志为依据。比较有效的检查方式是先明确接口约束，再检查可观察的不变量，例如空闲页数能否恢复、分配块是否重叠、伙伴是否真正合并，而不是仅凭“程序打印了成功”判断。

页表调试中，条件断点没有命中和局部变量超出作用域都需要结合当前执行路径分析。后续学习时，应能自己解释每个测试的作用，并独立复现关键结果；生成报告不等于已经掌握这些内容。

各模块的任务提示词见报告对应小节，汇总见 [prompt.md](prompt.md)。
