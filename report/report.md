## 一、实验目的

1. 跟踪一次 Trap 从硬件入口到 C 处理函数、再返回原执行流的全过程，分清哪些状态由硬件记录，哪些寄存器由软件保存。
2. 用同一套入口处理两类不同的事件：时钟到期时继续原执行流；本实验中遇到断点或非法指令时，跳过触发异常的指令再返回。
3. 用课程测试分别检查寄存器恢复、异常返回地址和连续时钟中断，避免仅凭一行启动输出判断实现正确。

## 三、实验整体逻辑分析

以一次时钟中断为例：硬件记录 `sepc` 和 `scause` 等信息，按 `stvec` 转入汇编入口。硬件没有把所有通用寄存器自动压栈，这一步由 `SAVE_ALL` 完成。此时 `sp` 指向内核栈上的一份 `trapframe`，C 函数处理的就是这份现场。

```text
__alltraps → SAVE_ALL → 把 sp 传给 trap(tf)
    → trap_dispatch → interrupt_handler 或 exception_handler
    → __trapret → RESTORE_ALL → sret
```

两种事件共用入口，但返回位置不同。时钟中断保留原来的 `epc`；断点和非法指令需要更新 `epc`，否则返回后还会执行同一条指令。

## 四、实验内容与实现

### 4.1 接入 Lab2 的内存管理

只迁移了 `page_init()` 和 Best-Fit 缺失的实现，保留 Lab3 框架的默认分配器以及分配、释放时的中断保护。Lab3 头文件没有沿用 Lab2 的全部地址宏，因此从本框架的 `KERNBASE` 和 `KERNTOP` 换算物理边界，而非直接复制整个旧文件。接入的目的，是使内核完成内存初始化，继续执行后面的 Trap 测试。

### 4.2 模块一：汇编入口和现场恢复

**负责人：** 2412509-王毅豪、2413446-黄泓懿。**实现位置：** `kern/trap/trapentry.S`。

`SAVE_ALL` 已经决定了栈上各字段的位置。我们的 spec 有两条关键约束：恢复代码必须按原布局取值；传给 C 的必须是这份现场的地址，而不是原栈顶。入口只需要把当前 `sp` 放入第一个参数寄存器 `a0`，再调用 `trap`。C 函数返回后，自然接到 `__trapret`。

恢复时先取出保存的 `sstatus` 和 `sepc` 写回 CSR，再恢复通用寄存器，**最后从槽位 2 恢复原来的 `sp`**。这个顺序有实际原因：在最后一次取数之前，`sp` 一直是访问当前栈帧的基址。提前改掉它，后面的加载就会从另一块内存取数。另一个细节是恢复**栈帧中的** `epc`：C 函数可能已经更新它，返回时必须使用新值。

### 4.3 模块二：中断与异常处理

**负责人：** 2412509-王毅豪、2413446-黄泓懿。**实现位置：** `kern/trap/trap.c`。

| 情况 | 提交版的处理方式 | 为什么这样做 |
| --- | --- | --- |
| S 模式时钟中断 | 调用 `clock_set_next_event()`，再将 `ticks` 加一；每 100 次打印一次。累计打印达到 `SHUTDOWN_AFTER` 后调用 SBI 关机。 | 一次定时只安排一次事件。漏掉重装，即使第一次计数正确，也不会持续收到中断。关机数的是**打印次数**，不是中断次数。 |
| 非法指令、断点 | 根据 `tf->cause` 输出异常种类和地址，读取 `tf->epc` 处的首个半字。在本实验的 16/32 位指令范围内，低两位为 `11` 时前进 4 字节，否则前进 2 字节。 | 固定加 4 会越过压缩指令后面的有效指令；不前进则会反复触发同一异常。 |
| 其他类型 | 已知的其他中断按类型提示；未知中断打印原因及现场；未专门处理的异常打印现场，不擅自推进 `epc`。 | 未知原因下猜测返回位置会掩盖错误，保留现场更有利于定位。 |

处理函数返回后，由汇编恢复现场并执行 `sret`。课程模板没有指定 `SHUTDOWN_AFTER` 的数值，我们将默认值设为 10：每 100 个 tick 打印一次，第十次打印后关机。

### 4.4 提示词设计与问题排查

完整任务提示词见 [prompt.md](prompt.md)。汇编模块的提示词强调布局、调用约定和 `sp` 的恢复时机；C 模块分别规定中断与异常对 `epc` 的处理，验收时分别观察返回后的寄存器和第二次以后的时钟事件。

黄泓懿在审查独立实现的第一版时发现，AI 按寄存器编号顺序恢复，过早加载了 `x2`。错误不在槽位编号，而在于加载 `x2` 本身就改变了后续取数的基址。他在提示词里补上“最后恢复 `sp`”并要求解释原因。时钟处理也有类似遗漏：初版只计数而没有安排下一次事件，于是把“能够收到第 200 次中断”列为验收条件，而不以第一行输出为准。

原始模板编译时报两个 handler 未声明：分发函数已经调用它们，定义处还是空的。黄泓懿独立环境的 OpenSBI 输出 `Next Address: 0`，则是内核尚未正确加载；调整加载方式后才进入内核。小组提交版在 QEMU 4.1.1 下使用课程原有加载方式，评分脚本未改。

## 六、实验总结与收获

| OS 原理中的概念 | 本实验中的对应与边界 |
| --- | --- |
| 现场保护与进程切换 | 两者都涉及寄存器，但本实验保存的是被打断执行流的现场。返回时没有选另一个进程，也没有切换地址空间。 |
| 异步中断与同步异常 | 时钟中断不由当前指令导致；断点和非法指令则与当前指令直接相关。差异最终体现在是否调整返回地址。 |
| 特权返回 | `sret` 按保存的状态和地址返回；它本身不替软件恢复全部通用寄存器，也不意味着一定返回用户态。 |
| 本次未覆盖的机制 | 时钟中断可以为抢占调度提供时机，但本实验没有就绪队列或时间片选择；也没有实现用户进程系统调用、缺页恢复或多核同步。 |

**AI 协作体会：** 检查 AI 给出的汇编时，我们最关心的不是有没有漏掉某个寄存器，而是每次加载用的基址是否仍然正确。时钟部分也一样：第一次进入处理函数只能证明入口接通了；连续到达 200 ticks，才能检验下一次定时事件确实被安排。
