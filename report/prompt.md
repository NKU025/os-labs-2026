# Lab3 任务提示词

本文按实验任务列出提示词，路径以课程源码根目录为准。模块一和模块二对应本次练习的两个 spec；另外两条用于接入 Lab2 和验收结果。

## 1. 接入 Lab2：只补内存管理缺口

```text
[PROMPT]
先对照 Lab3 新框架和我们 Lab2 已通过测试的实现，指出 pmm.c、best_fit_pmm.c 中各缺了什么，再做最小迁移。不要直接用旧文件替换新文件。我要保留 Lab3 的中断开关逻辑和原来的分配器选择。

[RELY]
Lab3 已有设备树接口、Page 结构、页号换算宏和空闲链表接口。Lab2 的 page_init() 和 Best-Fit 已有实现，但两版头文件的宏不一定相同。

[GUARANTEE]
物理页描述符放在内核末尾之后；内核、固件和描述符本身占用的页不进入空闲区。Best-Fit 在满足请求的空闲块中选最小的一块，释放时只合并物理相邻块。保持 Lab3 的自检和课程测试源码不变。

[SPECIFICATION]
1. 先核对 KERNBASE、KERNTOP 和虚实地址偏移在新框架中的定义。内核起点和可管理上界用 Lab3 已有接口换算；不要添加上一版框架才有的头文件，也不要直接写死本机一次启动得到的内存大小。
2. 验证设备树内存区间、页边界和描述符数组容量，确认空间足够后再初始化。剩余区间不足一页时不登记空闲页。
3. 只补齐 Best-Fit 管理器所需的结构、函数与接口，不改原有自检。保留 alloc_pages/free_pages 周围的中断保护，不引入 Buddy 或 SLUB。
4. 分开报告“编译能否通过”和“内核是否运行到内存自检成功”，不要把仅能生成镜像当成运行成功。
```

## 2. 模块一：Trap 汇编入口和现场恢复

```text
[PROMPT]
补全 kern/trap/trapentry.S 的 RESTORE_ALL 和 __alltraps。先读 SAVE_ALL 和 struct trapframe，把“保存位置、要恢复的值、恢复时仍需使用的寄存器”对应起来，再写汇编。我尤其想弄清楚：栈帧里的 sp 和现在用于取数的 sp 为什么不是同一个值？

[RELY]
SAVE_ALL 已经在内核栈上建立现场。trap(struct trapframe *tf) 是现成的 C 接口，RISC-V 第一个参数用 a0 传递。__trapret 后面已经有 sret。

[GUARANTEE]
trap() 收到的是当前这份栈帧的地址。它返回后，通用寄存器恢复到被打断前的值；sret 使用栈帧中的返回状态与地址，包括异常处理函数可能更新过的 epc。保持 SAVE_ALL、trapframe 布局和 trap() 签名原样。

[SPECIFICATION]
1. 依据已有保存代码确认槽位：x2 槽是进入 Trap 前的 sp；32、33 槽是 sstatus 和 sepc。不要按另一种内核的布局恢复，也不要把只供诊断的 cause 和 badvaddr 当成返回所需的 CSR 写回。
2. __alltraps 在保存之后按调用约定传递 trapframe 指针并调用 trap。调用结束后接回 __trapret，保持栈帧仍可寻址。不要另造栈帧或手工猜测返回地址。
3. 恢复 CSR 时若借用临时寄存器，要随后恢复它们自己的原值；x0 不需要写回。最后一次从这份栈帧取数时才恢复 sp。解释提前恢复 sp 后，下一条 LOAD 会从哪里取数。
4. 用原版断点/上下文测试检查寄存器和断点返回位置。区分“原模板因缺少 handler 而暂时编译失败”与“汇编恢复逻辑错误”，不要通过改测试或跳过断点获得通过。
```

## 3. 模块二：中断与异常处理

```text
[PROMPT]
在 kern/trap/trap.c 的练习区域完成 interrupt_handler 和 exception_handler。先列出时钟中断、断点、非法指令、未知原因四种输入各自应该改变哪些状态。尤其检查两个容易写错的地方：时钟什么时候安排下一次事件？哪些情况下应该修改 tf->epc？

[RELY]
trap_dispatch 已按 cause 最高位区分中断与异常。框架提供 clock_set_next_event、ticks、print_ticks、print_trapframe 和 SBI 关机接口。课程测试会检查规定的提示文字。

[GUARANTEE]
每次 S 模式时钟中断只计数一次并重装下一次事件；每 TICK_NUM 次输出统计，达到规定的打印次数后才关机。断点和非法指令必须能越过触发指令；时钟中断保留返回地址。未识别的类型保留足够的诊断信息。不改已有分发函数和评分脚本。

[SPECIFICATION]
1. 时钟分支里要区分“中断次数”和“已经打印的次数”。本框架 TICK_NUM 是 100；若没有给出 SHUTDOWN_AFTER 的数值，明确提出实现选用的默认值，并允许编译时覆盖，不要把这个默认值写成老师给定的数字。
2. 明确区分已知的其他中断、未知中断和未知异常。已知类型给相应提示；未知中断显示原因并打印 trapframe，未知异常打印 trapframe 后返回。不要对未知异常统一加 4。
3. 对本实验的非法指令与断点分别输出种类和地址；在推进 epc 前读触发地址处的首个半字。按当前 RV64IMAC 测试用到的 16/32 位编码判断实际长度，注意指令地址可能只按 2 字节对齐。
4. 分别说明三种故障会在运行时怎样表现：不重装定时器；不推进异常 epc；在压缩指令后固定加 4。用课程对应测试核对实现，不要在处理函数内直接输出测试的 PASS 标志。
```

## 4. 验收：区分编译、评分和正常启动

```text
[PROMPT]
请用未经修改的课程测试验收小组提交版。我要保留能复核的结果，不把组员独立环境中的启动参数或截图当作本机的运行结果。

[RELY]
评分分三项：断点前后现场、非法指令及兜底、持续时钟中断。普通启动另走正常关机路径。组内使用的 QEMU/OpenSBI 版本不同，内核加载方式要分别核对。

[GUARANTEE]
不改测试断言、固定字符串、分值或超时，不把旧日志当成一次新的运行；未验证的内容单独标明。

[SPECIFICATION]
1. 编译失败先保留第一条有意义的错误，区分模板缺少实现和新增代码引入的问题。运行停在固件阶段时，先看固件入口与镜像加载方式，再判断是否已执行到 Trap 代码。
2. 运行 make grade，逐项记录 PASS/FAIL 和总分。分别说明 Test 1 是否返回到寄存器校验、Test 2 是否越过非法指令、Test 3 是否持续达到 200 ticks；不要把总分泛化为用户态切换或缺页处理已验证。
3. 单独运行 make qemu，统计实际出现的“100 ticks”行数和退出状态。评分时达到 200 ticks 与正常启动达到关机阈值是两件事，分别记录。指出哪一段终端输出能验证关机条件。
```
